# Triage

Third-party threads are triaged on the same state machine as a maintainer's own tracker, with no maintainer to grill. This file holds the whole procedure, so nothing outside the skill is needed. A PR is an issue with attached code and takes the same roles.

## Roles

Every thread gets one category and one state.

- Category: `bug` (something is broken) or `enhancement` (new capability).
- State: `needs-triage` (a maintainer must evaluate), `needs-info` (waiting on the reporter), `ready-for-agent` (fully specified, an agent can take it), `ready-for-human` (needs human judgment or access), `wontfix` (will not be actioned).

The repo's label mapping decides the real label strings. With no mapping, the report records the canonical role and no label is invented. A label or comment lands only with TRIAGE or WRITE permission; otherwise the report records the recommended role. Conflicting state labels on one thread are flagged in the report, not resolved by guessing.

## Verify before judging

Record one of `confirmed (path:line@SHA)`, `failed`, `insufficient detail` (a `needs-info` signal). For a bug, reproduce from the reporter's steps. For a PR, check out the branch and run its tests or commands. Search the codebase by concept for an existing implementation: if the behavior already exists, the outcome is an already-implemented `wontfix` that points to where it lives. If the repo keeps an `.out-of-scope/` folder of rejected requests, read it and match by concept ("night theme" matches a dark-mode record).

## Outcomes

- `ready-for-agent`: post an agent brief (below).
- `ready-for-human`: same shape, plus why it cannot be delegated.
- `needs-info`: post the notes template (below) with specific, answerable questions, never "please provide more info".
- `wontfix`: close with a comment that depends on why. Already implemented: point to the implementation. Rejected bug: a polite explanation. Rejected enhancement: link the matching `.out-of-scope/` record if one exists; without WRITE the comment proposes the record.
- `needs-triage`: apply the role, with an optional comment on partial progress.

## Unattended deltas

- **Banner.** `> *This was generated by AI during triage.*` closes every comment as its last line, never the first, so the reader meets the content before the notice. The repo's required AI disclosure overrides the wording with its exact text, not the position. The issue or PR body carries the repo's own disclosure as its last line; a PR review comment counts as a triage comment. Run `preflight.py check-comment --body <file>` before posting a comment.
- **No maintainer present.** The smaller-reversible-action rule in SKILL.md applies. Interactive grilling and multi-thread attention sweeps belong to a maintainer's own triage.
- **Brief shape.** The repo's agent-brief template wins; else the template below.
- **Own tracker only.** Publishing specs or tickets to a tracker the author controls follows that tracker's labels. Third-party threads use the layouts in `bodies.md` and the repo's own templates.

## Agent brief

A brief is the contract an agent works from; the original thread is context. State what to do, not how, and keep it durable: name types, signatures and behavior, never file paths or line numbers, which go stale. Every acceptance criterion is independently testable, and out-of-scope items are explicit. For a PR, "current behavior" describes the state of the diff and the brief says what is left to finish.

```markdown
## Agent Brief

**Category:** bug / enhancement
**Summary:** one line

**Current behavior:** what happens now (for a PR, the state of the diff)
**Desired behavior:** what should happen, with edge cases and errors
**Key interfaces:** types, signatures or config shapes that change, and why

**Acceptance criteria:**

- [ ] specific, testable criterion

**Out of scope:**

- adjacent thing that stays untouched
```

## Needs-info notes

```markdown
## Triage Notes

**What we've established so far:**

- point

**What we still need from you (@reporter):**

- specific question
```

Everything resolved so far goes under "established", so no work is lost. On resuming a thread, read the earlier notes first and never re-ask a resolved question.
