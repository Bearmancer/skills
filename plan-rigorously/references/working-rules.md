# Working rules

- **Authority is a claim the engine cannot prove.** Confirmation subjects accept only authority `user` and an unhedged leading `yes` or `no` (the reason must be what the user actually answered in the question tool); a plan_change never takes `system` or `proposal`. A human typing it is guaranteed only by asking through the question tool.
- **Tier has a floor.** Risk signals force tier 2 and more tasks or surfaces than tier 0 allows force tier 1; `check` fails a plan that claims less.
- **Plans are given as paths** (`.rigor/plans/<slug>.plan.yaml`), never as a slug.
- **Spec and plan are separate files.** The spec says what and why and names code with stable *anchors*. The plan says how, where and in what order and holds paths. At plan time resolve each anchor through codegraph into `plan.resolved_anchors` with path, commit and `verified_at`; if it cannot be resolved mark it `stale` and the gate fails. Templates: `assets/spec.yaml`, `assets/plan.yaml` (a valid worked example).
- **Planner sizing:** inline or one planner subagent, chosen by task and surface counts (`planning.delegation` in `references/limits.yaml`); every task names its `surfaces`.
- **Proposal audit:** every proposal is audited by a fresh subagent that sees only the claim. External claims need two different tools, saved evidence files of the minimum length in `planning.audit.evidence`, and one primary source. Internal claims use codegraph and code. If fewer than two audit tools work, or no fresh subagent can be spawned for the audit, the verdict is unverifiable and that is a blocking question. Tool syntax marked UNVERIFIED in `audit-tools.yaml` must be read from `--help` first and recorded.
- **Reviews:** always independent subagents on the whole plan, never per task. Critic for tier 1 and up; Architect for tier 2 or interface, module, cross-cutting or schema risk; data and verification lenses by risk signal. Log each finding as `review_finding` with accepted or rejected and a reason. Re-review is sized by `check` (none, lint-only, targeted, full). Round cap: `planning.review.rounds_per_role` (per reviewer role); after that present the best version and record non-consensus. After a full review log `--kind review_complete --role <r> --plan <p> --set-baseline`.
- **Clarify stage.** State lives in `.rigor/clarify/`. Research tickets restate the question, cite sources and end with what is unverified; grilling tickets need the user's answer in the ledger. Parking an effort is the user's call. Tickets mirror one way to GitHub issues (dry run first); before publish and before `exec finish` the issues are read back and edits are sized: small is noted, medium asks the user, large blocks until the user accepts the drift. The local files stay the source of truth.
- **Sediment.** Settled terms go to `GLOSSARY.md` (definition plus avoided words), hard-to-reverse, surprising decisions with a real trade-off get an ADR, business rules go to `docs/business`; the spec names each file and a plan task writes it during execution. Out-of-scope items are fixed once confirmed; bringing one back is a `scope_change:<id>` user decision. The document language is recorded once in `meta.language`.
- **A changed answer later** triggers a delta replan of only the tasks the question blocks, logged as `plan_change` with authority `user`.
- **Existing plans:** `start` refuses to overwrite any incomplete plan. Ask the user: finish it, discard it explicitly, or choose another location (`--root <dir>` on every verb).
- **GitHub:** run `publish` (dry run) first, then `--yes`. It uses `gh api` (REST) throughout, searches open issues first (also in the dry run): exact title updates, a near match exits 3 and becomes a question, otherwise it creates a parent issue plus one sub-issue per task with labels issue, enhancement, and needs-review until reviews pass, then triaged. No remote means record a skipped G_publish with a reason.
