# P0-P1: intake, branch, ledger

Contract: gates, CLI and the state machine are in ../SKILL.md. This playbook is the detail for this phase.

## P0 and P1: intake, branch, ledger

1. **Name the destination first.** One or two lines: what reaching the end looks like (the spec, decision or change this effort finds its way to). Record it as the first decision row. Fog test: can the destination be stated in one sentence, and can the first three decisions be stated precisely even if none can be answered yet? Two yeses mean plan. Either no means the effort is fog: do not init a plan. Run `init --slug S --wayfinder`, record the destination attempt as a decision, add each unstatable question with `fog --add`, and work the map in `phases/W0-wayfinder.md`; only `G_WF` releases the effort into P0. A question is ticketed only when it can be stated sharply, even if it is blocked. Decisions live in exactly one place; any index line gists and links.
2. **Plan mode is sticky.** "Do / fix / build X" and "just do it" mean "plan X"; do not implement, not even through a subagent. One request makes one plan however large; an unclear request is not a reason to start over.
3. **Record the outcome and its evidence, not a vibe.** Write the outcome in one line and cite the request text. The route is deterministic: if any of the six intent fields is missing, run the intent interview in P3; if all six are present, go straight to the frontier. Record the route as a decision for audit, never as a gate. If the user asks to be interviewed, run the interview; if the outcome itself is fuzzy ("make auth better"), that is fog and belongs in W0, not a guess at the plan.
4. **Classify the issue type** (`--type`), which fixes the directory and the task-kind rules: `bug` (a defect: reproduce first, needs a `fix` task), `refactor` (behaviour preserved, needs a `refactor` task; G1 also requires `survey-*` facts and a `top-recommendation`), `audit` (a read-only review of issues or code ending in a report and recommended actions), `research` (decisions only), `feature`, `chore`, `docs`. Also claim a **size**: S (at most 2 tasks, 3 files, one capability, nothing irreversible), M, or L (more than 8 tasks or more than 2 capabilities; deep exploration, external research, adversarial lanes). Tiers: Trivial = 1 file; Standard = 1-5 files; Architecture = 5+ modules. For a high-risk M/S plan that is not size L, pass `--deliberate`; G3 otherwise triggers the deliberate record only on size L or an active `--irreversible` decision.
5. **Scope check (capability map).** Only when one request bundles several independently testable capabilities: distinct consumers or data, acceptance criteria that cluster into separately shippable groups, one capability cuttable without rewriting the others. Record `capability --id <stable-kebab> --responsibility <one line> --deps <ids>` before any spec work. Ids are chosen once and never renamed; dependencies point one way; a cycle means two capabilities are really one. Build order follows dependencies. The user approves the map (boundaries, direction, order) before specs and tasks; then specify, plan and task each module in dependency order. One capability: no map, no ceremony. Map shape: `| Module id | Responsibility | Depends on |` plus `Build order: a -> b, c -> d`.
6. **Auto branch.** In a git repo, `git switch -c plan/<slug>` (or `git switch plan/<slug>` if it exists); record it. Not a repo: `branch: null`, say so once. Never commit, push or open a PR.
7. **Init and gate.** `init --slug S --type T [flags]`, then `gate --id G0`. The artifacts are created by `init`, never by hand. A passing G0 advances the ledger to P1; `task` is refused until G3 and `publish` until G4, so the phase order is enforced, not narrated.
