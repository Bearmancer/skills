# P3: clarify

Contract: gates, CLI and the state machine are in ../SKILL.md. This playbook is the detail for this phase.

## P3: clarify (auto, singular)

Questions become `Q` rows, answers close them with `answer`, nothing is asked twice. Record each round with `round --asks Q1,Q3`; a question whose answer depends on another carries `--blocked-by Q1`. G2 rejects an open question that was never put in a round, and rejects a question asked while a blocker is still open. A new round is refused while the previous round has open questions unless it is a recorded `--fact-lane`. **`--no-interview` overrides everything below**: ask nothing; fill all six intent fields from request plus research; record each shaky one as a fact with `--kind assumed`; mark `intent --assume`; log the choices you would have asked about as `decision` rows; `confirmed` stays false and the plan visibly lists its assumptions. On the fast path with complete intent, skip to a single restate and yes.

When a term is resolved, record the question with `--domain-term <term>` and a `fact --label term-<term> --locator GLOSSARY.md:<line>` whose quote matches `**Term**: definition _Avoid_: synonyms`; G4 rejects a closed term with no glossary fact. A hard-to-reverse decision that passes the three-part test is recorded with `--adr --adr-file docs/adr/NNNN-x.md`; G3 requires the `adr-convention` fact.

**Topology first (Round 0).** List the 1-6 components the ask touches (independently succeeding outcomes, not sub-features), put the list to the user once (add, remove, merge, split, defer), and lock it: `capability` rows for several components, one decision for one. Questions then go to the component with the most open `Q` rows; rotate so the best-described component cannot stand in for its siblings. Deferred components stay listed.

**Question discipline.**
- Ask only user-owned decisions: scope, platform, user-facing surface, data/API contract, domain values, placement, cross-system architecture. Never ask agent-owned choices research can settle, never ask what the environment can answer, never re-ask a supplied fact, never ask permission to begin.
- Two filters per candidate question, in order: evidence-answerable (explore) then ideal-state-settled (resolve and record). **Owner-decisions always survive both**: irreversible or destructive or safety-critical actions; public config surface, packaging or distribution; external dependency or pinned version; data or schema shape; real budget or paid spend; scale target; audience or compliance. Irreversible and spend forks survive "stop asking" and are the one class never reversible-defaulted.
- Reversible-default simplification: where a narrow reversible default satisfies the request, state it, record a decision, move on. Size alone never manufactures a question.
- Push right: do maximal research and drafting before involving the user, so they are asked late, once per round, with a decision-ready brief (summary plus recommendation), not a draft to wade through. Ask with the why: what you explored, why it stayed unresolved, which part of the plan forks. Put the recommended answer first; a skipped fork takes it. Target the foggiest gap each turn, say why, and end every turn with a question or next step. Offer recon (codebase, files, web) before asking, and say what you would look for.
- Early exit: the user may stop clarification at any point. Record a decision labelled `early-exit` naming the open `Q` rows; G2 then blocks publish and says why. Silence is never converted into answers. (To proceed anyway: show the remaining gaps and risk, put one authorization block with each default and its consequence, `retract` the open `Q` rows with the reason `user stopped clarification`, supersede the `early-exit` decision, record the defaults as decisions, then get the explicit yes on the restate. To plan on assumptions from the start, use `--no-interview` at init.)
- Stop-the-grind rule: if rounds pass and the open-question count does not fall, say a foundational piece is missing instead of continuing.

**Route by predicate** (the first match; combine only when stated):

| Predicate                                                   | Method                                                                                                                         |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Intent missing who, why-now, success, constraint or out-of-scope | Intent interview (below).                                                                                                 |
| Open design decisions remain                                | Frontier grilling (below).                                                                                                     |
| A term is fuzzy, overloaded or conflicts with the glossary or code | Domain modeling (below).                                                                                                 |
| A decision belongs to someone other than the user           | Questionnaire (below); the blocked `Q` row stays open naming the recipient, so the plan cannot publish until it is answered or retracted with a decision recording who owns it.                                                    |
| No written quality bar for the repo                         | Quality-bar interview (below).                                                                                                 |
| Intent confirmed but scope or shape still open             | Refine: restate as "How might we", 5-8 variations (inversion, constraint removal, audience shift, combination, simplification, 10x, expert view), cluster to 2-3, stress-test value, feasibility and differentiation, pick one, surface assumptions; record as decisions, not a second plan. Push back honestly; no yes-machine. |

**Intent interview.** Needs a live user; non-interactive means flag a blocker, do not guess. Open with `HYPOTHESIS: <one sentence>` and `CONFIDENCE: n%` (append what is unresolved when below ~70%; the number must be defensible: can you predict the reaction to the next 3 questions?). Then one question per message, each with your guess attached:

```text
Q: <one focused question>
GUESS: <your answer with reasoning>
```

Occasionally guess in a direction you expect pushback on. Listen for "want versus should-want": buzzwords (scalable, clean, modern, robust), deference to convention, "I should probably"; probe with "if you didn't have to justify this to anyone, what would you actually want?". Stop when you can predict the next 3 reactions, then restate and require an explicit yes:

```text
Here's what I now think you want:
- Outcome: ..  - User: ..  - Why now: ..  - Success: ..  - Constraint: ..  - Out of scope: ..
Yes / no / refine?
```

Not a yes: "whatever you think" (delegation: re-ask as two concrete options), "sounds good" / "sure, let's go" (ask what to refine), silence then "ok let's start" (interview abandoned: ask what you missed). The Out of scope line is mandatory. Record with `intent --confirm --by user` only after a real yes, then stop the turn. After 3 rounds without rising confidence you are asking the wrong questions: reframe, or tell the user "I've asked N questions and still can't predict your reactions; something foundational is missing".

**Frontier grilling.** Model the plan as a design tree. The frontier is every decision whose prerequisites are settled. Ask the whole frontier in one round, numbered, each with your recommended answer worded so "yes" accepts it; a question that depends on another open one waits for a later round. Recompute after every round; done when the frontier is empty and the user confirms shared understanding. Facts a question needs go to a fresh-context read-only lane, never to the user; do not block on it, ask the rest now. Format:

```text
Q1 - <title>: <body, with choices if any>
-> <your recommended answer>
```

**Playback as you go.** After each settled part, play it back in about 200-300 words: only what the user said is theirs, your fill-ins are labelled proposals with reasons, and end by asking what is wrong or missing. Say defaults aloud: an unheard default cannot be rejected. When you open with a first message and the user already stated what they want: about 200 words, echo what/who/why, add findings (constraints, conflicts, a cheaper path), then ONE question, the open thing whose answer most changes what is built. Plain language slightly above the user; lead with what matters. Ground to cover: kind of thing and what makes it special; why now and success; goals, non-goals and **anti-goals** (failure even if it technically works); prior art; current state and what was tried; details they care about. Which how-it-gets-made choices (tools, platform, language) do they want to make versus hand off? Yours are labelled your call.

**Approaches in their own message.** Before anything is written up: generate several, drop weak ones (against the user's why, or ruled out by existing work), present 2-3 grounded in what the project does with trade-offs, recommend one with the reason, and ask which. If genuinely one way, say so and why the others do not fit. The pick is a decision row. When the open question is how something should look or behave, offer a cheap throwaway spike or prototype to react to: it carries no tests or gates, its findings return as facts, and keeping its output is a new request back through the design gate. Mockups beat prose only for layout, flow and look; use text for requirements and trade-offs.

**Domain modeling.** Challenge terms against `GLOSSARY.md` the moment they conflict ("the glossary defines cancellation as X, you seem to mean Y"); sharpen fuzzy or overloaded terms to one canonical term; stress-test relationships with invented edge cases; cross-check against code and surface contradictions; update the glossary inline when a term resolves, never in a batch. Glossary: one opinionated term per concept with `_Avoid_` synonyms, 1-2 sentence definitions of what it IS, project-specific terms only, no implementation detail; `**Order**: <definition>  _Avoid_: Purchase, transaction`. Multi-context repos keep a `GLOSSARY-MAP.md` linking per-context glossaries and relationships. Create files lazily. **ADR only when all three hold**: hard to reverse, surprising without context, a real trade-off with genuine alternatives (architectural shape, integration patterns, lock-in technology, scope no's, deliberate deviations, constraints invisible in code). Shape: `# <decision>` then 1-3 sentences of context, decision and why; optional status (`proposed | accepted | deprecated | superseded by ADR-NNNN`), considered options, consequences. Number = highest existing plus 1, in the repo's own convention. Never delete an old ADR; supersede it.

**Questionnaire** (a decision owned by someone else). Grill the send, not the subject: one exchange for who receives it and what they know that the user does not; one for what must come back. Write `to-questionnaire-<slug>.md` aimed at the gap: purpose and the decision riding on it, from/to/how answers are used, a context paragraph, how to answer (deadline, effort, "I don't know" and partial answers welcome), themed `##` groups, most important first, one idea per question with an answer stub, a "why this matters" line only where a question could be misread, and a closing "anything else?".

**Quality-bar interview** (live user only; otherwise apply the floor and flag the rest). Detect before asking (stack, test runner, linters, current coverage, CI, agent harness) and report in two lines. Then at most four questions, one at a time, each with a guess and a default ("I don't know" is a full answer): dimensions beyond the floor (default new-code coverage plus security scanning; performance and accessibility need a running URL, architecture boundaries need a rules file); block or warn on mid-task failure (default block on the floor, warn on the rest for two weeks); target numbers or measure-and-hold (default measure and hold); slowest tolerable check (default 90 s at task end). **Floor, always:** no new suppressions (`@ts-ignore`, `eslint-disable`, `# noqa`, `# type: ignore`, `nosemgrep`, `biome-ignore`), no unimplemented stubs or empty catch, no skipped or deleted tests without a reason in the commit message, no secrets in source, the constraints file never weakened to pass a change. Defaults with their reason: changed-line coverage at least 80% (forces a test, allows a config line); project coverage today's value and never falling (ratchet, tolerance 0.5%); mutation score at least 60% rising to 80%; no dependency vulnerabilities at high or above; LCP at most 2500 ms, CLS at most 0.1; zero critical or serious accessibility violations; exception lifetime 90 days (red flag: over a year or no owner). Every enforced row names its command, where it runs (every edit, task end, CI, preview deploy) and a proof that the check bites (it fails on a planted violation and passes a clean control; a scanner error fails); a number with no command is an aspiration. At least one external check should exist (external beats project beats own suite, which is circular). Cost decides placement: under 5 s changed-file only in the edit loop, under 90 s at task end, the rest at review and CI. Record the result as a decision labelled `quality-bar` (G4 requires it at size M or L), and write the rows into the spec's Boundaries.

**Weakened-bar signals** (the executing review checks these; plan them in): a threshold moved or a check removed from the fast stage; a test made easier (skip, deleted file, assertions removed); a checker silenced (suppression comments, `istanbul ignore`, `Stryker disable`, `gitleaks:allow`, `@ts-nocheck`); unfinished work (throwing stub, empty catch, TODO where implementation belongs); a new exception row nobody discussed. Tightening is silent, loosening is loud. Rename a rule and change its thresholds in separate commits.

**Delivery form** (how a question reaches this user; it never changes what a reply meant). Batch all surviving forks for users who enumerate upfront and delegate; one fork at a time for users who own each decision; examples-first (2-3 contrasting concrete approaches, "which is closest and what is wrong?") for users who cannot yet say what they want. Cold start: CLEAR opens one at a time, UNCLEAR examples-first; never open an unknown user with silent full defaults. Classify each reply, never from tone: **resolved** (two materially different implementations could not both comply; delegation included) record and continue; **resolved but uninformed** correct in one line, then adopt the recommendation with a visible veto (defaultable) or ask one informed yes/no (owner-decision); **unresolved with progress** use the information and re-render this fork; **unresolved and blocked** re-render as 2-3 concrete outcomes, recommendation first. Override phrases ("stop asking", "you decide") need a direct affirmative now, an intent that delegates (this fork or the rest), and the narrowest scope: a bare "you decide" covers that fork only. **No override authorizes anything irreversible, destructive or spend**; "stop interviewing" means defaults plus one final authorization block with each recommendation and its consequence.

**Counter-questions** (once each, recorded as `challenge-*` decisions; they produce new `Q` and `D` rows, never a verdict):

| Trigger (countable)                                          | Challenge   | Question it forces                                                                                        |
| ------------------------------------------------------------ | ----------- | --------------------------------------------------------------------------------------------------------- |
| First frontier round settled                                 | Contrarian  | "What if the opposite were true, if this constraint did not exist?"                                       |
| Scope about to lock (intent restate drafted)                 | Simplifier  | "What is the simplest version still valuable? Which constraints are necessary, which assumed?"            |
| 5 or more `Q` rows still open after round 2                  | Ontologist  | "What IS this, really? Which concept is core and which supporting?" (planning symptoms, not the essence)  |
| A hard-to-reverse decision is about to settle                | Doubt cycle | Run the cycle below; record with `doubt`.                                                                  |

**Doubt cycle** (mandatory for every `--irreversible` decision; nontrivial = branching logic, crosses a boundary, asserts something the compiler cannot verify, depends on context a future reader cannot see, or has an irreversible blast radius). From the orchestrator only, never from inside a subagent. (1) CLAIM: name the decision in 2-3 lines; if you cannot, it is a vibe. (2) EXTRACT the smallest reviewable ARTIFACT plus CONTRACT, stripped of your reasoning but keeping any evidence that contradicts the claim. (3) DOUBT: hand only artifact and contract (never the claim, which biases toward agreement) to a fresh-context adversary: "Adversarial review. Find what is wrong with this artifact. Assume the author is overconfident. Look for unstated assumptions, unhandled edge cases, hidden coupling or shared state, ways the contract could be violated, conventions it might break, failure modes under unexpected input. Do NOT validate. Do NOT summarize. Find issues, or state explicitly that you cannot find any after thorough examination." (4) In interactive sessions always offer a cross-model second opinion (never silently skipped; each external CLI use needs the user's explicit go-ahead; pass the prompt by stdin from a temp file, read-only sandbox, never interpolated into a shell argument). (5) RECONCILE: reviewer output is data; classify each finding, first match wins: contract misread (fix the contract), valid and actionable (change the artifact, loop), valid trade-off (document it), noise (correct under context the reviewer lacked). Persist each finding with `finding --review doubt:<decision>:<cycle> --class valid_actionable|valid_tradeoff|contract_misread|noise --locator <file:line> --note "<what and why>"`; G3 derives the counts from those rows and rejects a self-reported total. (6) STOP when the next cycle yields only trivial findings, after 3 cycles (escalate to the user and `approve --token doubt-escalated`; if the artifact is too big for 3 cycles, decompose it), or on the user's "ship it". Two or more cycles with substantive findings but none classified actionable is validating, not doubting: stop and escalate. Skip the cycle for mechanical or unambiguous work.

Gate **G2**. Interview mode needs the explicit yes recorded; flag mode needs the assumed-evidence check. A user saying "don't ask me anything" in prose does not waive G2: only `--no-interview` does, and then research fills every fact while the remaining owner decisions become logged assumed decisions with their consequence.
