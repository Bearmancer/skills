# P5: tasks and plan

Contract: gates, CLI and the state machine are in ../SKILL.md. This playbook is the detail for this phase.

**3. Tasks.** Write them into the ledger as tracer-bullet vertical slices in dependency order: each slice cuts a narrow complete path through every layer (schema, API, UI, tests), is demoable or verifiable on its own, and fits one fresh context. Never all-database then all-API then all-UI. Prefactor first ("make the change easy, then make the easy change"). Risk-first when a piece is unproven (prove the WebSocket before building on it); contract-first when parallel work shares an API (slice 0 defines the contract). Each task:
   - `files` (exact paths; modify ranges when known), `interfaces` (exactly what it consumes and produces, because the implementer sees only its own task), `acceptance` (checkable; no "works well"), `verify` (the exact command and expected result; every step ends on a completion criterion), `deps` (acyclic; `plan.md` must render `deps: T1,T2` or G4 fails), `kind`, optional `issue`, optional `est_lines`.
   - Sizing: XS 1 file, S 1-2, M 3-5, L 5-8, XL 8+ is too big. Split when a task spans more than one focused session (about 2 hours of agent work), cannot state acceptance in 3 bullets, touches 2+ independent subsystems, or has "and" in its title. A task is the smallest unit with its own test cycle that is worth a reviewer's gate; fold setup, config and docs into the task whose deliverable needs them; split only where a reviewer could reject one task while approving its neighbour. Roughly 100 lines changed is good, 300 acceptable as one logical change, 1000 gets split. Rule of 500: a change touching more than 500 lines is a codemod or scripted transform (G4 enforces via `est_lines`).
   - **Test contract with TDD on (default):** agree the seam with the user first. Record `test_seam` exactly as `"<interface> | catches: ... | misses: ... | class: in-process|local-substitutable|remote-owned|true-external"`, plus `test_file` (the test path), `red` (the failing test and its expected failure; a `fix` names its repro in red) and `green` (the minimal pass condition). The class is the dependency category from `codebase-design.md`; G4 rejects a seam without it. Red and green must be observably different; G4 rejects a missing or prose-only seam, a missing test file, or identical red/green. Executed evidence is recorded with `test-run --task T1 --phase red|green --cmd ... --exit ... --artifact ...`; a plan may publish without runs because it is planning, but any handoff that claims a test was run cites the run row. Good tests describe behaviour through the public interface, read like a spec, survive refactors, one logical assertion; expected values come from an independent literal, worked example or spec line, never recomputed the way the code does (tautological tests are banned); mock only at system boundaries (external APIs, time and randomness, sometimes the DB or filesystem), never your own modules; prefer real implementation over fake over stub over mock; verify through the interface, not a side channel. Pick test size by resources (small = one process no I/O; medium = localhost; large = external) and keep most tests small. Crash or rollback behaviour is exercised at the real boundary, not an injected exception.
   - **Kinds.** `fix`: the first step is a failing `repro` test (Prove-It); do not theorise first. `refactor`: preserve behaviour exactly (same outputs, errors, side effects and order); existing tests pass unmodified; characterization tests first; scope to what changed; understand before touching (Chesterton's fence: record a fact for why the thing exists, check blame); one simplification at a time; clarity over line count; never remove error handling; follow the project's conventions; never mixed into a feature task. `feature`, `docs`, `chore` as named. A change touching a lockfile is `chore` and acceptance records the changelog read, one dependency per change, and the lockfile diff reviewed.
   - **Incremental rules per slice:** simplest thing that could work; touch only what the task requires and write `NOTICED BUT NOT TOUCHING: ..` instead of fixing adjacent things; one logical thing per increment; keep it compiling with existing tests green; flag incomplete user-visible features; safe opt-in defaults; additive and reversible (migrations have rollback; no delete-and-replace in one commit); more than about 100 untested lines means stop and test. Put a verification checkpoint (tests, build, core flow, human review) after every 2-3 tasks and high-risk tasks early.
   - **Parallelism.** Safe: independent feature slices, tests for built features, docs. Sequential: migrations, shared state, dependency chains. Coordinate: a shared API contract is defined first. Record dependencies so `frontier` can tell an executor what is ready.
   - **Wide mechanical refactor** (rename a column, retype a shared symbol across thousands of call sites): not a tracer bullet. Expand (add the new form beside the old), migrate call sites in batches by blast radius (each its own task, blocked by expand, CI green throughout), contract (delete the old form once no caller remains, blocked by every migrate batch). If batches cannot stay green alone, share an integration branch and block a final integrate-and-verify task.
   - **Tracker mapping.** If the repo designates a tracker for tasks, `plan.md` stays markdown and notes the tracker, and its Tasks list is an ordered index of ids and links with no duplicate checklist.
   - After drafting, put slice granularity and blocking edges back to the user in one round before publish: the approved object is the task graph, not only the design.

**4. Verification and review plan.** `plan.md` renders the review bar from the script: the Standards and Spec axes, lenses, severity labels, presumptive blockers, change-size budget, dependency discipline, quality bar and a fresh-context reviewer. Add project-specific review criteria as decisions. When the executed work is reviewed, verify each comment against the codebase before implementing, clarify unclear items first, push back with evidence, and YAGNI-check "implement it properly" requests by grepping for real usage.

**5. Issues and ticket drafts.** Declare every source issue (`issue --ref`) and link tasks to them (`task --issue`). `render-issues` writes one draft per task: What to build (end-to-end behaviour from the user's side, interfaces and types, no file paths or line numbers beyond the task record, because they go stale; a prototype snippet that encodes a decision more precisely than prose is the one exception), Blocked by, Acceptance (a checklist of independently verifiable items), Verify, test seam and steps. Triage vocabulary: exactly one category (`bug` | `enhancement`) and one state (`needs-triage` before the plan is published, then `ready-for-agent`; also `needs-info`, `ready-for-human`, `wontfix`); drafts carry the labels as text, nothing is applied to a tracker. An agent brief is behavioural, not procedural: category, one-line summary, current versus desired behaviour including edge cases, key interfaces, acceptance criteria, explicit out of scope. A rejected enhancement is recorded once per concept (not per issue) with the durable reason and the prior requests, so the same idea is not re-suggested; already-implemented and bug rejections do not enter that list. Anything posted to a tracker later opens with `> *This was generated by AI during triage.*`. Filing, labelling or closing is a separate step the owner approves per batch, using the repo's issue-tracker conventions, with `-R owner/repo` on every command.

**6. Criteria discipline.** Every success criterion is binary and defined upfront: id, exact scenario (tool, inputs, pass condition), the evidence artifact expected, adversarial classes for heavier work, and a stop condition. A criterion that cannot fail is not a criterion; an activity objective ("investigate X") is not a goal. Tests alone never prove done: evidence comes from the real surface (HTTP, terminal, browser, or a CLI/DB diff for data-shaped work); `--dry-run`, a printed command or "looks correct" never counts; evidence is tied to the tree it was produced on and goes stale when tracked content changes. State each goal with an outcome (what is true), literal deliverables, binary criteria, constraints, and a WHEN TO STOP line ("I'll stop when <observable state>"). Light work gets 1-2 criteria (happy path, riskiest edge); heavy work (new module, auth, external integration, schema change, concurrency, cross-domain refactor) gets 3 or more (happy, edge, regression, adversarial). Quantify: a bug fix is a failing case before and the same passing after; performance is a metric, target, method and run count; tests are the exact command and condition. Never invent a budget, token limit or deadline.

**7. Render and gate.** `render`, `render-issues`, then `gate --id G4`. Fix every `ERROR`; `WARN` lines are advisory. Never hand-edit `plan.md` ahead of the ledger (render refuses to overwrite hand edits unless `--force`, and publish refuses a hand-edited plan).

**8. Handoff.** `plan.md` renders the restart summary and the executor rules (fresh context per task, no parallel overlap, review and 5-round cap, stop reasons, rulings, worker statuses, ledger lines, restart block). This skill starts nothing.

**9. Writing the plan.** The reader has no chat history: a fresh session must act from the text alone. Every rule is checkable and carries its why; one meaning has one home; do not restate what scripts, layout or `--help` already say, only the unwritten convention, the reason, the gotcha. Number procedures of three or more steps, end every step on a completion criterion, state when every deferral lands, phrase rules positively (pair a hard prohibition with what to do instead), use one term per referent, and end the plan on a next action startable in under two minutes.
