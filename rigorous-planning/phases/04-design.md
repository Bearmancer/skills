# P4: design and spec

Contract: gates, CLI and the state machine are in ../SKILL.md. This playbook is the detail for this phase.

## P4: design and maximal plan

**1. Spec first.** Surface assumptions before writing spec content; every silent fill-in becomes an assumed fact or an open `Q` row, never prose (`ASSUMPTIONS I'M MAKING: 1.. 2.. -> correct me now or I proceed`). Reframe vague requirements as measurable criteria. The rendered `## Spec` holds **Objective** (what, why, user, success), **User stories** (`decision --label user-stories --decision "As a <actor>, I can ..."`; G4 requires at least one `As a` line for a feature at size L), **Commands** (full executable commands with flags, discovered from the repo's own scripts, wrappers and CI, never an assumed `npm test`), **Project structure**, **Code style** (one real snippet beats paragraphs), **Testing strategy** (framework, locations, levels), **Boundaries** (Always / Ask first / Never), **Success criteria** (specific, testable), **Open questions** and **Further notes** (`decision --label further-notes`). Synthesize from what is known; do not interview in this step. Record the project's commands as a decision labelled `commands` and its boundaries (including quality-bar rows) as one labelled `boundaries`; the rendered Spec embeds both. Record each risk as `decision --label risk-<n> --decision "<risk> | <H/M/L impact> | <mitigation>"`; G4 requires the mitigation and they render under Risks. If the repo already uses an external spec system (OpenSpec or similar), keep its format and storage and do not create a duplicate.

**2. Design in the open.** Record approaches considered (2-3, one trade-off line each), the chosen one, seams and interfaces, and what is out of scope, each settled choice as a `decision` (mark `--adr` when it passes the three-part test, `--irreversible` when it is hard to undo).
- Vocabulary: **module** = anything with an interface and an implementation, at any scale; **interface** = everything a caller must know (signature plus invariants, ordering, error modes, config, performance); **depth** = leverage at the interface (much behaviour behind a small interface; shallow = interface nearly as complex as implementation); **seam** = where behaviour can change without editing in place, the location of a module's interface; **adapter** = a concrete thing satisfying an interface at a seam; **leverage** = caller payoff; **locality** = maintainer payoff (change, bugs and verification concentrate in one place). The interface is the test surface; wanting to test past it means the shape is wrong. **One adapter is a hypothetical seam, two is a real one**: no seam unless something varies across it.
- Dependency categories decide testing across a seam: in-process (merge and test through the new interface, no adapter); local-substitutable (test with the stand-in, internal seam); remote but owned (define a port, inject the transport, in-memory adapter for tests); true external (inject as a port, mock adapter in tests). Replace, do not layer: delete old unit tests on shallow modules once tests exist at the deepened interface, assert observable outcomes, survive internal refactors. Testability: accept dependencies, return results instead of side effects, keep the surface small.
- When the interface itself is contested, design it twice: frame constraints, dependencies and their category; then have 3 or more fresh-context lanes each produce a radically different interface (minimize to 1-3 entry points; maximize flexibility; optimize the most common caller; ports and adapters where a dependency crosses a seam), each returning interface, usage example, what it hides, dependency strategy and trade-offs. Compare in prose on depth, locality and seam placement, give an opinionated recommendation, and propose a hybrid only when elements combine well.
- Large or high-risk plans add a consensus pass. The hard trigger is size L, an active `--irreversible` decision, or `--deliberate`; for auth/security, data migration, destructive, compliance/PII or public-API risk, mark the decision `--irreversible` or pass `--deliberate` rather than relying on a text match. Record as active decisions: `principles` (>=3 items), `drivers` (>=3), `option-a`+`option-b` or `options`+`invalidation`, `pre-mortem` (>=3), `expanded-test-plan` (all of unit, integration, e2e, observability). G3 enforces the counts and tokens; the prose below is the method that produces them. Then two independent reviews of the same fixed snapshot: an architect lane (strongest steelman antithesis against the favoured option, at least one real trade-off tension, a synthesis path) and a critic lane (principle-option consistency, fair alternatives, risk-mitigation clarity, testable criteria; reject shallow alternatives, driver contradictions, vague risks); the critic never sees the architect's output; only you combine them. This split is a method, not a separate gate: persist the findings as `plan-review` rows and keep the existing 3-cycle cap. Revise and repeat up to 3 rounds; at 3 present the best version and say there is no consensus. If the design passes the three-part test (hard to reverse, surprising without context, a real trade-off with genuine alternatives), it carries an ADR with the source-minimal shape: decision, context and why, alternatives, consequences, follow-ups; record it with `--adr-file`. If it does not, keep drivers, pre-mortem and alternatives as decisions in the plan and do not manufacture an ADR.
- Plan review (default on). Before asking for approval, have a fresh-context reviewer read the draft spec, design and task graph with only that text. Builder check: "You have been handed this design and asked to plan it; you cannot talk to its author. Report only the questions you would still need answered: where you would have to guess and a wrong guess would matter, each with why the answer changes the plan, ranked; skip what the design leaves to the builder or you could decide yourself; if nothing important is left, say so." Then self-review: spec coverage (each requirement has a task), step scan (each step lets the implementer write exactly one reasonable thing), name and type consistency across tasks, five input classes the spec implies but no task tests, proportion (a plan several times longer than the spec is a transcript). Sort findings into three piles: answered already (put the answer in the plan), minor (settle yourself and mark it your call), the user's (only they can answer; bring them in ONE message, most important first, one round only). Persist every finding as a row: `finding --review plan-review:<cycle> --class valid_actionable|valid_tradeoff|contract_misread|noise --locator <file:line> --note "<what and why>"`. A genuinely clean review is `plan-review --cycle n --clean --scope <what was reviewed>`; a clean header with no scope or with non-noise findings is a G3 error. Counts are derived from the rows, never supplied. Stop after 3 cycles or when only trivial findings remain.
- Approval: if a capability map exists, it is approved first (`approve --gate G3 --token approve-capability-map --by user --quote "<the user's exact words>"`). Then `approve-design` with the same quote. Spec and design approval happens before tasks exist, never in the same breath as writing them. Timeout, a dismissed prompt, "sounds good" about the idea, or "go ahead and plan" is not approval, and neither is the original request. Under `--no-interview`, G3 instead requires the logged assumed decisions (and a `*capabilit*` decision naming every capability when a map exists). Run the doubt cycle for each irreversible decision before this gate: `doubt --id D1 --claim "<the decision in 2-3 lines>" --cycle n`, then persist each finding with `finding --review doubt:<Dn>:<cycle> --class ... --locator ...`; a clean cycle uses `--clean --scope <artifact>`. Mark the ADR path on the decision itself with `--adr-file`.
