# Seams: deep modules

Contract: gates, CLI and the state machine are in ../SKILL.md. This playbook is the detail for this phase.

**2. Design in the open.** Record approaches considered (2-3, one trade-off line each), the chosen one, seams and interfaces, and what is out of scope, each settled choice as a `decision` (mark `--adr` when it passes the three-part test, `--irreversible` when it is hard to undo).
- Vocabulary: **module** = anything with an interface and an implementation, at any scale; **interface** = everything a caller must know (signature plus invariants, ordering, error modes, config, performance); **depth** = leverage at the interface (much behaviour behind a small interface; shallow = interface nearly as complex as implementation); **seam** = where behaviour can change without editing in place, the location of a module's interface; **adapter** = a concrete thing satisfying an interface at a seam; **leverage** = caller payoff; **locality** = maintainer payoff (change, bugs and verification concentrate in one place). The interface is the test surface; wanting to test past it means the shape is wrong. One adapter is a hypothetical seam, two is a real one: no seam unless something varies across it.
- Dependency categories decide testing across a seam: in-process (merge and test through the new interface, no adapter); local-substitutable (test with the stand-in, internal seam); remote but owned (define a port, inject the transport, in-memory adapter for tests); true external (inject as a port, mock adapter in tests). Replace, do not layer: delete old unit tests on shallow modules once tests exist at the deepened interface, assert observable outcomes, survive internal refactors. Testability: accept dependencies, return results instead of side effects, keep the surface small.
- When the interface itself is contested, design it two ways: frame constraints, dependencies and their category; then have 3 or more fresh-context lanes each produce a radically different interface (minimize to 1-3 entry points; maximize flexibility; optimize the most common caller; ports and adapters where a dependency crosses a seam), each returning interface, usage example, what it hides, dependency strategy and trade-offs. Compare in prose on depth, locality and seam placement, give an opinionated recommendation, and propose a hybrid only when elements combine well.
- Large or high-risk plans (size L, auth/security, data migration, destructive or irreversible, compliance/PII, public API break) add a consensus pass: draft Principles (3-5), Decision Drivers (top 3) and at least 2 viable Options with bounded pros and cons (if only one is viable, state why the rest are invalid); a deliberate pre-mortem (3 failure scenarios) and an expanded test plan (unit, integration, e2e, observability). Then two independent reviews of the same fixed snapshot: an architect lane (strongest steelman antithesis against the favoured option, at least one real trade-off tension, a synthesis path) and a critic lane (principle-option consistency, fair alternatives, risk-mitigation clarity, testable criteria; reject shallow alternatives, driver contradictions, vague risks); the critic never sees the architect's output; only you combine them. Revise and repeat up to 3 rounds; at 3 present the best version and say there is no consensus. The final design carries an ADR: decision, drivers, alternatives considered, why chosen, consequences, follow-ups. Record the outcome as decisions.
