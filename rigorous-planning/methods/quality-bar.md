# Quality bar

Contract: gates, CLI and the state machine are in ../SKILL.md. This playbook is the detail for this phase.

Record the result as `decision --label quality-bar --decision "<the rows that must hold>"`; G4 requires that exact label at size L, and a number with no command is an aspiration.

**Quality-bar interview** (live user only; otherwise apply the floor and flag the rest). Detect before asking (stack, test runner, linters, current coverage, CI, agent harness) and report in two lines. Then at most four questions, one at a time, each with a guess and a default ("I don't know" is a full answer): dimensions beyond the floor (default new-code coverage plus security scanning; performance and accessibility need a running URL, architecture boundaries need a rules file); block or warn on mid-task failure (default block on the floor, warn on the rest for two weeks); target numbers or measure-and-hold (default measure and hold); slowest tolerable check (default 90 s at task end). **Floor, always:** no new suppressions (`@ts-ignore`, `eslint-disable`, `# noqa`, `# type: ignore`, `nosemgrep`, `biome-ignore`), no unimplemented stubs or empty catch, no skipped or deleted tests without a reason in the commit message, no secrets in source, the constraints file never weakened to pass a change. Defaults with their reason: changed-line coverage at least 80% (forces a test, allows a config line); project coverage today's value and never falling (ratchet, tolerance 0.5%); mutation score at least 60% rising to 80%; no dependency vulnerabilities at high or above; LCP at most 2500 ms, CLS at most 0.1; zero critical or serious accessibility violations; exception lifetime 90 days (red flag: over a year or no owner). Every enforced row names its command, where it runs (every edit, task end, CI, preview deploy) and a proof that the check bites (it fails on a planted violation and passes a clean control; a scanner error fails); a number with no command is an aspiration. At least one external check should exist (external beats project beats own suite, which is circular). Cost decides placement: under 5 s changed-file only in the edit loop, under 90 s at task end, the rest at review and CI. Record the result as a decision labelled `quality-bar` (G4 requires it at size M or L), and write the rows into the spec's Boundaries.

**Weakened-bar signals** (the executing review checks these; plan them in): a threshold moved or a check removed from the fast stage; a test made easier (skip, deleted file, assertions removed); a checker silenced (suppression comments, `istanbul ignore`, `Stryker disable`, `gitleaks:allow`, `@ts-nocheck`); unfinished work (throwing stub, empty catch, TODO where implementation belongs); a new exception row nobody discussed. Tightening is silent, loosening is loud. Rename a rule and change its thresholds in separate commits.
