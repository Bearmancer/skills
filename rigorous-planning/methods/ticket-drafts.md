# Ticket drafts and triage

Contract: gates, CLI and the state machine are in ../SKILL.md. This playbook is the detail for this phase.

**5. Issues and ticket drafts.** Declare every source issue (`issue --ref`) and link tasks to them (`task --issue`). `render-issues` is allowed only after G3 and writes one draft per task: What to build (end-to-end behaviour from the user's side, interfaces and types; no file paths or line numbers in the draft body because they go stale — the task record keeps them; a prototype snippet that encodes a decision more precisely than prose is the one exception), Blocked by (the task `deps`, rendered as names; a native tracker later turns them into blocking links), Acceptance (a checklist of independently verifiable items), Verify, test seam and red/green contract. A draft is not sent anywhere. Triage vocabulary: exactly one category (`bug` | `enhancement`) and one state (`needs-triage` before the plan is published, then `ready-for-agent`; also `needs-info`, `ready-for-human`, `wontfix`); drafts carry the labels as text, nothing is applied to a tracker. An agent brief is behavioural, not procedural: category, one-line summary, current versus desired behaviour including edge cases, key interfaces, acceptance criteria, explicit out of scope. A rejected enhancement is recorded once per concept (not per issue) with the durable reason and the prior requests, so the same idea is not re-suggested; already-implemented and bug rejections do not enter that list. Anything posted to a tracker later opens with `> *This was generated by AI during triage.*`. Filing, labelling or closing is a separate step the owner approves per batch, using the repo's issue-tracker conventions, with `-R owner/repo` on every command.
