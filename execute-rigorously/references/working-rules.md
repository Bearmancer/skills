# Working rules

- **Start conditions** (`exec start` refuses otherwise): plan final, `check --final` green, authorized, rendered after the final check, feedback commands and delivery mode given by the user, main checkout clean. A failure means back to `plan-rigorously`; never fix the plan here. A needed plan change is a question and a logged `plan_change`.
- **Docs are written here.** Glossary, ADR and business-fact files named in the spec are created by their plan tasks inside the worktree, in the same commit flow as code; planning wrote none of them.
- **Drift.** `finish` reads the mirrored issues back; small edits are noted, medium ones ask the user, large ones block until the user accepts.
- **What the engine refuses.** Starting a task while another is started; a task whose `blocked_on` question is open; a third try after the same failure twice; `vtask` with files the plan does not declare; `red` with a harness exit code; a verifier who implemented or already verified; a second baseline; `--topology inline` on a plan sized for subagents; `finish` with uncommitted worktree changes. Verifier and reviewer identity are names the orchestrator supplies; the engine rejects reuse but cannot prove a fresh context. An explicit user request outside the plan is recorded as a follow-up (`reported`) and the user is told to run `plan-rigorously`.
- **One loop per plan.** Existing run: finished, report and stop; interrupted (stale heartbeat), `exec start` resumes it in the same worktree and branch; live, refused; plan changed, refused until the user says `discard`.
- **Topology** by size: inline or one fresh implementer per task, chosen by task and surface counts (`execution.delegation` in `../plan-rigorously/references/limits.yaml`). With implementers the orchestrator never edits product files. Briefs carry pointers (task id, plan, spec), not pasted text; reports stay within `execution.report` with a status of DONE, DONE_WITH_CONCERNS, BLOCKED or NEEDS_CONTEXT.
- **Retries.** Attempt cap, repeated-failure stop and free harness repairs are `execution.retries` in `limits.yaml`. A runner or environment failure that never exercised the product gets the free repair (`--harness`). Then `task --status blocked --reason`; dependents block automatically; report it.
- **Feedback baseline.** Failures already present in the baseline are warnings unless they mention a planned file; anything new must be fixed before `verify` passes.
- **Verification is a different context from the author.** One verifier pass per wave or phase, not per task; verdicts confirmed, false-positive, needs-fix, needs-human-review. Reviewers are the roles planning routed; re-review is none, lint-only, targeted or full by share of the branch changed. Each fix is proven test-first. Review rounds are capped by `execution.reviews`.
- **Adversarial classes** apply by trigger (`exec-routing.yaml`); probe each applicable class and record the rest as not applicable.
- **Amending an acceptance criterion** keeps the original verbatim with reason, evidence, authority and time. Silent deletion or weakening is invalid.
- **One worktree per plan.** Branch `rigor/<slug>` lives in `.rigor/exec/wt`, one commit per task. Phases are checkpoints inside it, not branches.
- **Delivery is exactly what the user chose in the front batch.** `squash-merge` (the user authorized delivery): push, open the PR and squash-merge it through `gh api` (REST, so it also works where GraphQL is blocked), delete the local and remote branch. `branch` (not authorized): nothing leaves the worktree. `finish` stops on the first failing step and can be re-run.
- **Away mode (`--away`, from the front batch):** a limit hit blocks that task and its dependents, independent work continues, and the question is queued (`check` lists it). `finish` refuses while any queued question is unanswered. Not away: stop and ask at once.
- **Plan defects found mid-run:** block the affected tasks, ask the user; the plan is untouched until a logged `plan_change` says otherwise.
